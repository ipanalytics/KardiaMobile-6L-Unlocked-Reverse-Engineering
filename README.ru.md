# KardiaMobile 6L Unlocked — реверс-инжиниринг

_English version: [README.md](README.md)_

**Реверс BLE-протокола AliveCor KardiaMobile 6L: рукопожатие, побайтовый формат потока и прямой клиент под Linux, который пишет ЭКГ без приложения производителя, без аккаунта и без облака.**

KardiaMobile 6L отдаёт кардиограмму только своему телефонному приложению — по BLE, через вендорский сервис с недокументированной командой разблокировки. Меня это достало: прибор лежит на столе, сервер стоит рядом, а мои собственные данные о сердце всё равно едут через чужой аккаунт и возвращаются пятистраничным PDF.

Я разобрала протокол. Теперь кардиограмму пишет мой код под Linux — по воздуху, без приложения, без аккаунтов, без облака.

Ниже не теория: байты вынуты из реального HCI-лога, снятого на телефоне, проверены на живом приборе — частота дискретизации, кадрирование и токен разблокировки совпадают до последнего байта.

* * *

## Протокол коротко

У 6L один **вендорский сервис**, и вся работа идёт на двух его характеристиках:

| UUID | Роль | Свойства |
| --- | --- | --- |
| `ac060001-328c-a28f-9846-5a8aa212661b` | сервис | — |
| `ac060002-328c-a28f-9846-5a8aa212661b` | управление | write, indicate |
| `ac060003-328c-a28f-9846-5a8aa212661b` | поток ЭКГ | notify |

Порядок ровно тот, что делает приложение:

1. **Сначала бонд.** Без шифрованного линка прибор не работает — подробности ниже.
2. Записать команду разблокировки в `ac060002` — 20 ASCII-байт, `M2 K<токен>`.
3. Подписаться на indications `ac060002` (записать `02 00` в его CCCD).
4. Подписаться на notifications `ac060003` (записать `01 00` в его CCCD).
5. Прибор отвечает `01` и начинает лить отсчёты в `ac060003`.

### Токен разблокировки вычисляется, его не выдают

Команда — обычный ASCII. Случайными выглядят только последние восемь байт:

```
M2 Kfeaa7255122d948f
```

Это не секрет с сервера — суффикс считается из того, что прибор и так рекламирует:

```
token = sha256("Triangle" + <рекламируемое BLE-имя>)[:8]   # hex, 8 байт
```

С рекламируемым именем `Kardia6L XXXX` из этого получается ровно та команда, что снята в логе. Ни аккаунта, ни похода на сервер, ни персонального секрета: «разблокировка» — это рукопожатие, а не удостоверение.

### Поток — 300 Гц, два канала, нарезанный по MTU

Отсчёты идут **парами int16 little-endian**, вперемешку:

```
<канал 1 int16 LE> <канал 2 int16 LE> <канал 1 int16 LE> <канал 2 int16 LE> ...
```

- Два канала, примерно 300 отсчётов в секунду на канал.
- Полный кадр — **9 пар (36 байт)**, когда MTU поднят, и **5 пар (20 байт)** на штатных 23 байтах: прибор подрезает кадр под MTU.
- Отсюда следствие: декодер обязан **накапливать байты и резать их на пары**, а не рассчитывать на фиксированный размер кадра. Хвост короче 4 байт — неполный, его выбрасываем.

Сырые значения — коды АЦП вокруг плавающей базовой линии; ЭКГ — это разница, поэтому первым делом надо убирать дрейф, а не верить абсолютным числам.

## Что здесь оказалось нетривиальным

**1. Нет бонда — нет данных.** На нешифрованном линке прибор отвечает на подписку `GATT Protocol Error: Unlikely Error (0x0E)` (а на чтения — `ATT Error: Insufficient Authentication (0x05)`). BlueZ сам сопряжение не поднимает: линк встаёт и молча остаётся незашифрованным. Лечится явным Just Works-сопряжением *до* подключения: без PIN и без ключей, но сам бонд обязателен.

**2. Бонд легко сделать наполовину.** Если вести `bluetoothctl` в batch-режиме и отправить `quit` сразу после `pair`, сопряжение рвётся на полпути: на приборе остаётся `Trusted: yes, Paired: no, Bonded: no`. С хоста это выглядит успехом и падает на каждой записи. Пары нужно дать завершиться.

**3. Размер кадра врёт.** В одном снятии те же данные идут кадрами по 20 байт, в другом — по 36. Кто прибьёт длину гвоздями, получит декодер, который работает на телефонном линке (MTU 23) и ломается на нашем (MTU поднят).

**4. Реклама включается касанием.** У 6L нет ни кнопки, ни светодиода. Он включается и рекламируется только пока замкнуты два верхних электрода — то есть пока его держат в руках, — и замолкает, как только контакт снят. Плюс он держит только **одно** соединение: если прибор занят приложением на телефоне, Linux не увидит ничего полезного.

## Как воспроизвести

Нужен Linux с Bluetooth-адаптером, BlueZ и Python 3 (`bleak`). Двумя пальцами замкните два верхних электрода и держите — это и включает прибор, и удерживает линк.

Клиент в `tools/` делает всю последовательность: бонд, разблокировка, подписки, поток, разбор в CSV и отчёт с графиком.

```
python3 tools/kardia_ble.py --scan          # найти прибор: имя и тип адреса
python3 tools/kardia_ble.py --auto          # бонд, разблокировка, 60 с записи, файлы ЭКГ
```

`--out DIR` задаёт папку для файлов (по умолчанию текущая), `--raw` сохраняет сырые
байты уведомлений рядом с CSV — для работы с протоколом, а `--wait SEC` задаёт, сколько
`--auto` ищет прибор.

Каждая сессия даёт:

- `ecg_<время>.csv` — два канала, строка на отсчёт, 300 Гц;
- `ecg_<время>.png` — трасса ритм-полосой;
- `ecg_<время>.pdf` — отчёт для печати.

## Как это вскрывалось

Протокол не угадывался и не перебирался — он вычитан из трафика:

1. Включила **HCI snoop log** на Android — система пишет весь обмен Bluetooth в файл `.cfa`.
2. Запустила приложение, сделала запись, забрала снятие.
3. Разобрала снятие как L2CAP/ATT: соединения, обнаружение сервисов, каждая запись и каждое уведомление, по порядку.
4. Нашла команду разблокировки — запись 20 ASCII-байт — и восстановила её суффикс.
5. Опознала поток, измерила кадрирование и частоту (2001 уведомление → 18009 пар → 300 Гц).
6. Подтвердила токен хешем рекламируемого имени: он воспроизвёл снятые байты точно.
7. Повторила последовательность на живом приборе: бонд, разблокировка, подписки, 60 секунд реальной ЭКГ.

## Статус

- Протокол вскрыт и проверен на живом приборе — **готово**.
- Прямой BLE-клиент под Linux, реальная ЭКГ в виде CSV/PNG/PDF — **работает**.
- Метрики качества (детекция комплексов, пульс, ВСР) — **работают, доводятся**: сухие пальцы и слабый прижим уводят вход в насыщение в первые секунды, из-за чего запись может быть настоящей и при этом непригодной для измерений.
- Шестой отведение (LL/RA) — **не разобрано**: приложение считает усиленные отведения из двух сырых каналов; в потоке их два, и шесть это проект не обещает.
